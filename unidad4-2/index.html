Unidad 4.2 — Integración de Tecnologías: Interoperabilidad, Seguridad y Escalabilidad¶

Objetivo de la sección

Entender qué se necesita para que una tecnología nueva funcione dentro de una organización real: conectarla con los sistemas que ya existen (interoperabilidad), protegerla y proteger los datos que maneja (seguridad), y diseñarla para que siga funcionando cuando crezca la demanda (escalabilidad). Al final se debe poder justificar decisiones de arquitectura con criterios técnicos y de riesgo.

En la Unidad 2 se estudiaron las tecnologías por separado: un modelo de machine learning, una plataforma de big data, un agente, la nube. En una organización real nada de eso llega a un terreno vacío. El modelo necesita datos que viven en tres sistemas distintos, el agente necesita acceso a información que no cualquiera debe ver, y el servicio que funcionaba con diez usuarios en el piloto se cae cuando lo usan mil. La hoja de ruta de la sección 4.1 identificó los sistemas heredados, la seguridad y la falta de capacidad como riesgos frecuentes; esta sección explica cómo se gestionan.

Interoperabilidad¶

La interoperabilidad es la capacidad de sistemas distintos para intercambiar información y usarla de forma significativa. El adjetivo importa: que dos sistemas puedan enviarse un archivo no significa que se entiendan. El Marco Europeo de Interoperabilidad (Comisión Europea, 2017) distingue cuatro capas, que sirven como lista de revisión para cualquier proyecto de integración:

CapaPregunta que respondeEjemplo de problema
Técnica¿Los sistemas pueden conectarse y transmitirse datos?Un sistema antiguo no tiene ninguna interfaz de conexión
Semántica¿Los datos significan lo mismo para ambos?Un sistema registra la edad en años y otro la fecha de nacimiento; “cliente activo” tiene definiciones distintas en cada área
Organizacional¿Los procesos y responsabilidades están alineados?Nadie es responsable de corregir un dato que llega mal de otra área
Legal¿La normativa permite compartir esos datos?Los datos de un paciente no pueden salir del sistema sin su autorización

La mayoría de los proyectos de integración que fracasan no lo hacen por la capa técnica, que suele tener solución, sino por la semántica y la organizacional: nadie acordó qué significan los datos ni quién responde por ellos. Un caso típico es el de la clínica de la sección 3.1: sus tres sistemas de historiales identifican al mismo paciente con códigos distintos. Conectarlos técnicamente es el menor de los problemas; lo difícil es decidir cuál es el identificador oficial y construir un índice maestro de pacientes que relacione los tres. En el sector salud existen estándares abiertos para esto, como HL7 FHIR, que define cómo representar e intercambiar información clínica a través de interfaces web. Usar un estándar abierto, en lugar de formatos propios, reduce el costo de cada nueva integración y el riesgo de depender de un solo proveedor.

Interfaces de programación (APIs)¶

Una API es la forma controlada en que un sistema le ofrece sus datos o funciones a otro. Es el mecanismo central de la integración moderna. La mayoría se construye con el estilo REST: se accede a recursos mediante direcciones web, con las operaciones estándar del protocolo HTTP (leer, crear, modificar, eliminar) y respuestas en un formato de texto estructurado como JSON. El servicio que se construyó en la sección 3.4 para exponer el modelo de predicción es un ejemplo: otro sistema le envía los datos de un cliente y recibe una predicción, sin saber nada de cómo funciona el modelo por dentro.

Una API bien diseñada se trata como un contrato entre quien la ofrece y quien la usa. Eso implica varias prácticas:

  • Documentación formal del contrato, por ejemplo con la especificación OpenAPI, que describe qué recursos existen, qué datos recibe cada uno y qué devuelve.

  • Versionado: cuando la API cambia, las versiones anteriores siguen disponibles durante un tiempo, para no romper a quienes ya la usan.

  • Autenticación y autorización: saber quién llama y qué puede hacer. El estándar más usado para delegar acceso es OAuth 2.0.

  • Una puerta de entrada única (API gateway) que centraliza la autenticación, el control de volumen de peticiones y el registro de uso.

Patrones de integración¶

Hay varias formas de conectar sistemas, y cada una resuelve un problema distinto. Hohpe y Woolf (2003) catalogaron los patrones de integración empresarial; los más relevantes para una transformación digital son los siguientes:

PatrónCómo funcionaVentajaLimitaciónCuándo usarlo
Punto a puntoCada sistema se conecta directamente con cada otroRápido para dos o tres sistemasCon n sistemas hay hasta n(n-1)/2 conexiones: se vuelve inmanejableIntegraciones pequeñas y estables
Concentrador (hub) o busLos sistemas se conectan a un intermediario central que enruta y traduceCada sistema nuevo requiere una sola conexiónEl intermediario es un punto único de falla y un posible cuello de botellaMuchos sistemas que deben hablar entre sí
API sincrónicaUn sistema pide algo y espera la respuestaSimple, respuesta inmediataSi el otro sistema cae o tarda, el primero también fallaConsultas en tiempo real (por ejemplo, pedir una predicción)
Mensajería y eventosUn sistema publica un mensaje en una cola y otro lo procesa cuando puedeLos sistemas quedan desacoplados; resiste caídas temporalesMás complejo de construir y de depurarFlujos continuos o picos de carga (por ejemplo, cada cita agendada genera un evento)
Integración por lotes (ETL)Se extraen, transforman y cargan datos periódicamente hacia un repositorio centralMuy usada para analítica; no exige que los sistemas de origen cambienLos datos no están en tiempo realAlimentar un lakehouse o un modelo de machine learning (sección 2.2)

Sistemas heredados¶

Un sistema heredado (legacy) es un sistema antiguo que sigue siendo crítico para la operación, pero que es difícil de modificar o integrar: a menudo está escrito en tecnologías obsoletas, tiene poca documentación y quienes lo construyeron ya no están. La tentación es reemplazarlo todo de una vez; casi siempre es un error, porque esos sistemas contienen reglas de negocio que nadie recuerda y detener la operación para migrarlos es muy riesgoso. Hay cuatro estrategias, de menor a mayor intervención:

  • Encapsular: dejar el sistema intacto y envolverlo con una API que lo exponga al resto. Es la más rápida y la que menos riesgo introduce, a costa de no resolver los problemas internos del sistema.

  • Migrar gradualmente: reemplazar funcionalidades de a una, de modo que el sistema nuevo vaya absorbiendo al viejo hasta que este pueda apagarse. Fowler (2004) llamó a este enfoque el patrón de la higuera estranguladora (strangler fig), por la planta que crece alrededor de un árbol hasta sustituirlo.

  • Reemplazar: construir o comprar un sistema nuevo y cambiar de un solo golpe. Solo es razonable cuando el sistema es pequeño o su riesgo de operación es bajo.

  • Retirar o mantener: si el sistema ya no aporta, se apaga; si funciona bien y no estorba la estrategia, se deja como está. No todo lo viejo es un problema.

Seguridad¶

Cada integración nueva abre caminos que antes estaban cerrados: una API, una cuenta de servicio, un repositorio con datos consolidados. La superficie de ataque crece con cada conexión, y los datos que antes estaban dispersos en tres sistemas ahora están reunidos en uno, un blanco más atractivo. La seguridad no se agrega al final del proyecto: se diseña desde el principio (security by design).

La base conceptual es la tríada CIA: proteger la confidencialidad (que solo vea los datos quien debe), la integridad (que los datos no se alteren sin autorización) y la disponibilidad (que el sistema esté disponible cuando se necesita). Un buen análisis de seguridad considera las tres: un sistema perfectamente confidencial que se cae todo el día también falla.

Identificar las amenazas¶

Antes de elegir controles hay que preguntarse qué puede salir mal. El modelado de amenazas hace esa pregunta de forma sistemática; el marco más conocido es STRIDE, que ordena las amenazas en seis categorías (Shostack, 2014):

AmenazaQué esEjemplo en la clínica
Spoofing (suplantación)Hacerse pasar por otroAlguien usa las credenciales de un coordinador
Tampering (manipulación)Alterar datos sin autorizaciónModificar el historial de un paciente
Repudiation (repudio)Negar haber hecho una acción sin que haya forma de probarloUn usuario borra datos y no queda registro
Information disclosure (divulgación)Exponer información a quien no debe verlaUna API devuelve datos de otro paciente

Elevation of privilege (elevación de privilegios)Obtener más permisos de los asignadosUn usuario común accede a funciones de administrador

Confianza cero (zero trust)¶

El modelo tradicional de seguridad era como un castillo con foso: se protegía el perímetro de la red y todo lo que estaba adentro se consideraba confiable. Con trabajo remoto, servicios en la nube y múltiples integraciones, ese perímetro ya no existe de forma clara. La arquitectura de confianza cero (NIST, 2020) parte del principio contrario: no se confía automáticamente en nadie ni en nada por estar dentro de la red. Sus ideas centrales son verificar explícitamente cada acceso (con identidad, dispositivo y contexto), dar el mínimo privilegio necesario y diseñar como si una intrusión ya hubiera ocurrido (assume breach), de modo que el daño quede contenido.

Privacidad y protección de datos personales¶

Cuando los datos son personales, además de ser un tema técnico, la seguridad es una obligación legal. En Colombia, la Ley 1581 de 2012 establece el régimen general de protección de datos personales: exige, en general, la autorización informada de su titular para el tratamiento y establece un trato especial para los datos sensibles, entre los que están los de salud; la Superintendencia de Industria y Comercio es la autoridad de control. Las organizaciones que atienden a residentes de la Unión Europea deben además cumplir el Reglamento General de Protección de Datos (GDPR). Dos prácticas ayudan a cumplir y a reducir el riesgo: la minimización de datos (recoger y conservar solo lo estrictamente necesario) y la anonimización o seudonimización cuando el dato personal no es indispensable, por ejemplo para entrenar un modelo. Las normas cambian y tienen detalles de aplicación, por lo que en un proyecto real conviene validarlas con el área jurídica.

Seguridad en proyectos de inteligencia artificial¶

Los sistemas de IA agregan riesgos propios sobre los anteriores. Los datos de entrenamiento pueden ser manipulados (envenenamiento de datos) para sesgar el modelo; el servicio de predicción puede filtrar información sensible de los datos con que se entrenó; y los agentes que usan herramientas (sección 2.3) pueden ser engañados mediante instrucciones maliciosas escondidas en un texto que procesan (prompt injection) para ejecutar acciones que no debían. La defensa principal es la misma de siempre aplicada con cuidado: cada herramienta del agente debe tener el mínimo de permisos, las acciones de alto impacto deben pedir confirmación humana, y todo lo que el agente hace debe quedar registrado. OWASP, una organización dedicada a la seguridad de aplicaciones, mantiene listas de los diez riesgos principales tanto para APIs como para aplicaciones basadas en modelos de lenguaje, útiles como lista de verificación.

Seguridad en el ciclo de desarrollo e incidentes¶

Las prácticas de DevSecOps integran la seguridad en el flujo de integración continua de la sección 3.2: cada cambio de código pasa automáticamente por revisiones de dependencias vulnerables, búsqueda de credenciales olvidadas en el código y análisis de las imágenes de contenedor, antes de llegar a producción. Es el mismo principio de la puerta de calidad del proyecto de MLOps, aplicado a la seguridad. Aun así, ningún sistema es invulnerable, por lo que se necesita un plan de respuesta a incidentes: quién decide, cómo se detecta, cómo se contiene el daño, cómo se recupera el servicio y qué se aprende después. Para organizar todo el programa de seguridad existen marcos de referencia: la norma ISO/IEC 27001 define un sistema de gestión de la seguridad de la información certificable, y el Marco de Ciberseguridad del NIST (versión 2.0, 2024) organiza el trabajo en seis funciones: gobernar, identificar, proteger, detectar, responder y recuperar.

Escalabilidad¶

La escalabilidad es la capacidad de un sistema de mantener su desempeño cuando aumenta la carga: más usuarios, más datos o más peticiones. Un sistema que funciona perfecto en el piloto con cincuenta usuarios y se vuelve inutilizable con cinco mil no es escalable. Se aborda desde el diseño, porque cambiar la arquitectura después es mucho más caro.

Hay dos formas básicas de crecer:

  • Escalamiento vertical: darle más recursos a la misma máquina (más memoria, más procesadores). Es simple, pero tiene un límite físico y de costo, y sigue habiendo un punto único de falla.

  • Escalamiento horizontal: agregar más máquinas que se reparten el trabajo. No tiene un techo tan evidente y mejora la tolerancia a fallos, pero exige diseñar el sistema para que pueda repartirse, y lo vuelve más complejo.

Aquí aparece la elasticidad, una característica de la nube que se vio en la sección 2.5: los recursos crecen y se reducen automáticamente con la demanda, y se paga solo por lo que se usa. Escalabilidad y elasticidad no son lo mismo: la primera es la capacidad de crecer; la segunda, la de crecer y encogerse de forma automática.

Una decisión frecuente de arquitectura es si construir el sistema como un monolito (una sola aplicación) o como microservicios (muchos servicios pequeños e independientes, descritos por Newman, 2021). Los microservicios permiten escalar cada parte por separado y que equipos distintos trabajen sin pisarse, pero introducen la complejidad de un sistema distribuido: más conexiones que fallan, más monitoreo y más costo operativo. Para un equipo pequeño o un producto que apenas empieza, un monolito bien organizado suele ser mejor elección; los microservicios se justifican cuando la escala o el tamaño de la organización lo exigen.

Medir el desempeño y la disponibilidad¶

No se puede gestionar lo que no se mide. Las medidas más usadas son la latencia (cuánto tarda una petición en responderse) y el rendimiento (throughput, cuántas peticiones por segundo se atienden). Kleppmann (2017) recomienda no mirar el promedio de la latencia sino los percentiles: el percentil 95 (p95) es el tiempo por debajo del cual se responde el 95 % de las peticiones, y muestra la experiencia de los usuarios que peor lo pasan, que es la que el promedio esconde. Para verificar la capacidad antes de que llegue la demanda real se hacen pruebas de carga, que simulan miles de usuarios.

La disponibilidad se expresa como el porcentaje del tiempo en que el servicio funciona, y se acuerda con los usuarios mediante un acuerdo de nivel de servicio (SLA), respaldado internamente por objetivos de nivel de servicio (SLO). Los porcentajes que parecen casi iguales significan cosas muy distintas:

DisponibilidadTiempo máximo sin servicio por añoPor mes (30 días)
99 %3,65 días7,2 horas
99,9 %8,76 horas43,2 minutos
99,99 %52,6 minutos4,3 minutos
99,999 %5,3 minutos26 segundos

Cada nueve adicional cuesta bastante más que el anterior, porque exige redundancia, monitoreo continuo y personal de guardia. Por eso la pregunta correcta no es “cuánta disponibilidad se puede tener” sino “cuánta disponibilidad necesita este servicio”. Para el tablero de seguimiento de los coordinadores, un 99 % puede ser suficiente; para el sistema que registra una atención de urgencias, no.

Para saber lo que ocurre con un sistema en producción se necesita observabilidad: recoger y analizar sus registros (logs), sus métricas y el recorrido de cada petición entre servicios. Es el equivalente, para todo el sistema, de lo que el monitoreo de deriva hace para un modelo de machine learning (sección 3.4).

Decidir y documentar la arquitectura¶

Todas las decisiones de esta sección implican compromisos: un concentrador simplifica las conexiones pero crea un punto único de falla; más seguridad suele significar menos comodidad; más disponibilidad cuesta más. No existe una respuesta correcta general, solo una adecuada al contexto. Por eso conviene dejar por escrito cada decisión importante, con el contexto, las alternativas consideradas, la decisión y sus consecuencias. Esta práctica se conoce como registro de decisiones de arquitectura (architecture decision records, Nygard, 2011) y evita que, meses después, nadie recuerde por qué se hizo algo de cierta manera.

Errores frecuentes al integrar tecnologías¶

  • Empezar por el código y no por el contrato: conectar sistemas sin acordar antes qué significan los datos y quién responde por ellos.

  • Integración punto a punto sin freno: cada conexión rápida parece barata, pero la suma se vuelve ingobernable.

  • Querer reemplazar el sistema heredado de golpe: se pierden reglas de negocio que nadie documentó y se pone en riesgo la operación.

  • Dejar la seguridad para el final: corregir una arquitectura insegura es mucho más caro que diseñarla bien desde el comienzo.

  • Credenciales dentro del código: una de las fallas más frecuentes y más fáciles de evitar.

  • Dar permisos amplios “para que funcione”: violar el mínimo privilegio por comodidad en la fase de pruebas y no corregirlo después.

  • Diseñar para el piloto y no para la escala: un servicio que guarda estado en cada petición no se puede repartir fácilmente entre varias máquinas.

  • Exigir cinco nueves sin necesidad: pagar una disponibilidad que el negocio no necesita.

Para tu proyecto final

Para la organización elegida en tu proyecto final: (1) dibuja un diagrama de arquitectura que muestre los sistemas existentes, la capa de integración y los servicios nuevos, indicando qué patrón de integración usa cada conexión; (2) elabora una tabla de al menos cinco amenazas de seguridad y privacidad (puedes usar STRIDE) con el control que las mitiga; (3) define los requisitos de escalabilidad del servicio principal (carga actual, carga esperada a dos años y disponibilidad objetivo) y la estrategia para cumplirlos; y (4) elige una estrategia para integrar un sistema heredado de la organización y justifica la decisión.

Glosario de términos clave¶

Interoperabilidad: capacidad de sistemas distintos para intercambiar información y usarla de forma significativa, en las capas técnica, semántica, organizacional y legal.

API (interfaz de programación de aplicaciones): forma controlada en que un sistema ofrece sus datos o funciones a otro. Se trata como un contrato.

REST: estilo de diseño de APIs sobre HTTP, que accede a recursos mediante direcciones web y suele intercambiar datos en formato JSON.

API gateway: puerta de entrada única a un conjunto de APIs, que centraliza la autenticación, el control de tráfico y el registro.

Estándar abierto: especificación pública que cualquiera puede implementar, lo que reduce la dependencia de un proveedor.

Sistema heredado (legacy): sistema antiguo, aún crítico para la operación, difícil de modificar o integrar.

Índice maestro de pacientes (o de clientes): registro central que relaciona los distintos identificadores que una misma persona tiene en sistemas distintos.

Tríada CIA: confidencialidad, integridad y disponibilidad, los tres objetivos básicos de la seguridad de la información.

Superficie de ataque: conjunto de puntos por los que un atacante podría intentar entrar a un sistema.

Mínimo privilegio: principio según el cual cada persona o programa recibe solo los permisos que necesita.

Confianza cero (zero trust): modelo de seguridad que no confía automáticamente en ningún usuario o dispositivo por estar dentro de la red, y verifica cada acceso.

Defensa en profundidad: superposición de varias capas de protección, de modo que la falla de una no exponga todo.

DevSecOps: integración de la seguridad en el flujo automatizado de desarrollo y despliegue.

Escalabilidad vertical y horizontal: crecer dándole más recursos a una máquina, o agregando más máquinas que se reparten el trabajo.

Elasticidad: capacidad de aumentar y reducir recursos automáticamente según la demanda.

Latencia y rendimiento (throughput): tiempo que tarda una petición en responderse, y número de peticiones atendidas por unidad de tiempo.

SLA y SLO: acuerdo de nivel de servicio con los usuarios, y objetivo interno que lo respalda.

Observabilidad: capacidad de entender el estado interno de un sistema a partir de sus registros, métricas y trazas.

Preguntas de repaso¶

  1. ¿Por qué se dice que la mayoría de los problemas de integración no son técnicos? Ilustra con un ejemplo de problema semántico y uno organizacional.

  2. Una organización tiene ocho sistemas que necesitan intercambiar datos. ¿Cuántas conexiones requeriría una integración punto a punto completa y cuántas una con concentrador? ¿Qué riesgo introduce el concentrador?

  3. Una empresa quiere conectar un modelo de predicción a un sistema de facturación de quince años de antigüedad, sin interfaces. Propón una estrategia de integración y justifícala frente a la alternativa de reemplazar el sistema.

  4. Elige tres de las seis categorías de STRIDE y, para un servicio que expone predicciones a otros sistemas, describe una amenaza concreta y el control que la mitigaría.

  5. Explica con tus palabras por qué un modelo de seguridad de confianza cero responde mejor al trabajo remoto y a los servicios en la nube que el modelo de perímetro.

  6. Un servicio debe tener 99,9 % de disponibilidad mensual. ¿Cuántos minutos puede estar caído al mes? ¿Por qué no siempre conviene pedir 99,999 %?

  7. ¿En qué casos elegirías un monolito y en cuáles microservicios para un producto nuevo? Justifica con dos criterios.
